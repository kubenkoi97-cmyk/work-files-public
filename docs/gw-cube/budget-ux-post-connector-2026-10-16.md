# JW Cube · Budget UX — этап 2 после коннектора

Статус: QUEUED, BLOCKED. Очерёдность строго: 1) завершение и проверка бюджетного коннектора; 2) внедрение компактного интерфейса бюджета по дополнительному техническому заданию; 3) остальной roadmap. Не менять код второго этапа до завершённого первого.

Основное: сохранить существующий «Месячный бюджет» без пересоздания; отдельная кнопка-иконка «Баланс и личные лимиты» вне ⋯; popup фактических счетов и свободных категорий; лёгкий зелёный плюс для добавления категории; ⋯ → Настройки, Capital, История и Диаграммы; проценты расходов открываются по маленькой кнопке %, а не видны постоянно. Раздельные карточки доходов, расходов и крупных обязательств; мягкая зебра и белый фон; сезонные цвета заголовков; скрытые технические ID и настройки.

Емкость категорий: не менее пяти новых доходов, семи расходов, семи крупных платежей, семи целей и семи личных лимитов. Не дублировать расходы, переносы, остатки, копилки и гипотетические заработки. Не объявлять черновик оплатой. Синхронизация через проверенный коннектор с revision, idempotency и read-after-write. Тесты на адаптивность, перенос, баланс, 80%/150% прогресса, CRUD и отсутствие дублирования. Приватные данные не публиковать.


## 1. Сначала исследовать реальное приложение, а не проектировать заново

1. Найди существующий компонент встроенного шаблона «Месячный бюджет» / Budget, его настройки, хранение категорий, пользовательские планы, факт, счета, цели, диаграммы, меню ⋯ и modal/drawer. Запиши реальные пути, exports, типы и схемы API; не выдумывай endpoints.
2. Найди текущую задачу Codex по бюджетному коннектору, её статус, ветку, открытый PR, тесты и очередь. Пока коннектор не закончен, только зарегистрируй эту работу как NEXT после него и вернись к текущей задаче.
3. Составь матрицу сохранности: существующие месяцы, пользовательские категории, исходный/действующий план, операции, статусы, лимиты, копилки, валюта, источники, локализация. Не удаляй и не перенумеровывай существующие сущности. Новые UI состояния не должны создавать альтернативную базу.
4. Используй текущий design system: то, что уже работает, сохранять; вносить incremental changes с минимальным diff и постепенным внедрением, без второго параллельного Budget.

## 2. Точный главный экран месяца

- Заголовок месяца — крупный и понятный. Цвет **по сезону**: осень тёплый мягко-оранжевый/терракотовый; зима светло-голубой; весна нежно-зелёный; лето светло-жёлтый. Шрифт тёмный, контраст WCAG. Не окрашивать фон всего экрана.
- Сохранять существующие поступления и расходы без перерисовки всей структуры. Поступления — зелёные акценты, расходы — оранжевые, отдельные крупные платежи — мягкий фиолетовый, история — голубой; никаких розовых блоков.
- Белые либо почти белые промежутки между карточками, аккуратная внешняя граница каждого блока, ненавязчивая «зебра» внутри любого табличного списка. Цвет всей строки равномерен; исключить видимые «ступеньки» на стыках ячеек.
- **Третья смысловая категория: «Обязательства и крупные платежи»**, отдельный компактный блок/сворачиваемая подгруппа; общая сумма расходов не должна включать крупные платежи дважды. Не отображать в списке десяток служебных колонок.
- Ресурсная часть: показать **«Остаток с прошлого месяца»** рядом с поступлениями одной строкой, суммой и без технического списка банков. Это перенесённый капитал, а не новое событие `income`; не создавать/подтверждать синтетическую доходную операцию и не удваивать итог. Банки выводить в другом окне.
- Два горизонтальных индикатора плана: зелёный **«Доходы + перенос»** и оранжевый **«Расходы»**, одинаковое начало слева и корректная шкала. Числа с € полностью видны, процент/tooltip — только по необходимости.
- Всё длинное переносится, строки/диаграммы не пересекаются, карточки имеют небольшое белое расстояние, on mobile 320/360/390 px — без горизонтального прокручивания главной страницы.

## 3. Главная новинка: иконка «Баланс и личные лимиты» — вне ⋯

- Рядом с названием/верхними действиями встроенного Budget поместить **отдельную маленькую, но хорошо обнаруживаемую иконку кошелька**, предпочтительно `wallet-cards` из действующего icon pack (при отсутствии — ближайший существующий). Tooltip/aria-label «Баланс и личные лимиты». Важно: это самостоятельная иконка **ВНЕ** меню ⋯.
- Клик/тап: modal/popover на desktop, bottom sheet/drawer на mobile; закрытие по крестику/Escape/подложке, возврат фокуса на кнопку, без смены выбранного месяца.
- Внутри две большие цифры разных близких зелёных оттенков:
  **«Карты и наличные — без копилок»**: реальное подтверждённое состояние доступных счетов с краткой разбивкой (банк/карта, наличные, другие подключённые счета).
  **«Свободные сейчас»**: деньги за вычетом уже ограниченных назначений по правилам текущей модели и список оставшихся персональных лимитов по выбранным категориям.
- Неизвестные значения показывать тире и пометку «неизвестно», а не произвольный ноль. Не смешивать гипотетический доход с банковским остатком; реальные цели/копилки не прибавлять как второй физический счёт и не вычитать повторно.
- Под цифрами компактный список категорий («Продукты», «Питомец», «Топливо» и т.п. — это **примеры, не хардкодить**). По умолчанию 5–7 любимых; остальные через «Показать ещё», reorder/edit/hide. Все данные берутся из существующих категорий пользователя.
- Рядом с категориями маленький **зелёный +**: выбрать существующую категорию либо добавить новую, задать сумму планового лимита €, подтвердить; мгновенно показать её в popup. Не открывать тяжёлые настройки, не создавать двойную категорию из-за регистра/пробелов/варианта эмодзи.
- Данные обновляются после успешной операции/синхронизации; показывать timestamp и статус в деталях, не вечно крутящийся индикатор. Ошибки и несверенные суммы видны честно.

## 4. Меню ⋯ только для редких инструментов

- `⋯ → Настройки`: единый редактор плановых статей, категорий, счетов, лимитов и параметров с понятными полями, ненавязчивыми подсказками; без видимых внутренних ID, raw JSON и служебных списков.
- `⋯ → Capital / Накопления`: popup с крупной кольцевой диаграммой **фактически накопленного**, корректной легендой «цель · сумма · процент», empty state, планом и расстоянием до цели отдельно, действиями «Отложить/Снять» через валидированные операции. Не путать сценарный план отложения с фактическим резервом.
- `⋯ → Статистика / Диаграммы`: существующие графики/селекторы, категории, динамика и корректный период, без дублирования старых компонентов. Легенды переносятся или переупаковываются, графики не перекрываются.
- `⋯ → История`: подробные строки дат, контрагентов, источников и доказательств по запросу. Не внедрять 12 технических колонок в основной экран.
- Сохранить прочие существующие пункты ⋯. Полное управление с клавиатуры, touch, screen reader; локаль ru-RU, € и исходные валюты без случайной конвертации.

## 5. Маленький значок % возле каждого расхода

- В каждой строке категории расходов **мини-кнопка %**, прогресс-полосы постоянно не показывать. По нажатию — popover: план €, подтверждено потрачено €, остаток €, доля % и аккуратная горизонтальная полоса.
- Формула: `percent = actual_confirmed / planned * 100` для положительного плана. Например, условные 24 € из 30 € = 80%. При факте выше плана показывать 150%, полосу визуально ограничивать 100% и обозначать перерасход. Plan = 0 → «вне плана» вместо деления на ноль; ноль/неизвестно различать.
- Черновик, ожидание, спор или неподтверждённая запись не становятся `actual_confirmed` от отображения. Адаптивное всплытие без наложения на другие элементы. Триггер имеет aria-label и удобную touch-area.


## 6. Работающие новые категории, не «пустые нарисованные строки»

**Обязательная емкость по каждому месяцу/шаблону**: минимум **5** новых статей доходов, **7** новых статей расходов, **7** крупных обязательств, **7** целей накопления, **7** дополнительных категорий свободных лимитов. Не показывать всем сразу 33 пустых поля — одна компактная `+` в каждом разделе, по нажатию мини-редактор.

Модель изменения:
1. Выбрать соответствующий раздел и нажать зелёный `+`.
2. Указать понятное название, выбрать существующую категорию либо создать новую, ввести план € (число неотрицательно); сохранить.
3. Запрос проходит валидацию/транзакцию коннектора. Создаётся стабильный системный ID и ссылка на текущий период и правильный тип операции.
4. Сразу после успешного read-after-write категория отражается в этом месяце, сумме ресурсов/расходов и, где уместно, в аналитике и балансе. Не ждать обновления браузера.
5. Для каждого дополнительного месяца копировать/распространять статью только по явному выбору. Новая категория в справочнике может быть общей, а план/факт каждого периода — независимым.
6. Редактирование существующей строки: **пустая коррекция** сохраняет базовый исходный план, **0** намеренно обнуляет активный план, **число** заменяет активный план. Нулевой план не означает погашенный долг или отказ от права.
7. Физическое удаление категории при связанных операциях не выполнять: скрытие/архивирование с сохранением history; возможное переименование не меняет ID и предшествующие ревизии.
8. Для накоплений новое название является новой *целью*, но деньги не возникают, пока не проведена подтверждённая операция. Для лимита новая категория является *представлением* подтверждённых расходов, а не новым расходом.

Особое правило: категории расходов и обязательств могут отображаться раздельно, но в master totals оплаченный или запланированный платёж учитывается **один раз**. Кредит/кауцион/спорное требование классифицируются без автоматического признания долга и без «completed» при смене статуса. Строки без названия/категории/числовой суммы в агрегаты не включаются.

## 7. Синхронизация с ChatGPT и внешним финансовым источником

После прохождения Stage Gate интеграция обязана использовать **настоящий budget CRUD API** и не имитировать изменения записью в текстовую заметку. До этого момента помечать все операции синхронизации как недоступные, не обещать, что запись в Cube состоялась.

- Canonical entity: stable `budgetId/monthId/categoryId/planLineId/transactionId/accountId/goalId/debtId` либо реальные существующие типы, не придумывать параллельные идентификаторы. Mapping Google Sheets ↔ приложение ↔ ChatGPT connector хранить приватно, с `sourceRef/version/revision/updatedAt/evidenceId`.
- Расход/доход, план/факт, подтверждено пользователем/подтверждено банком, условный сценарий, disputed claim, счет, целевой фонд, копилка — **разные бизнес-смыслы**. Нельзя объявлять forecast банк-фактом, receipt оплатой другой статьи, депозит вторым доходом.
- Изменение в одной разрешённой системе: прочитать актуальные данные и версии, проверить целевые поля и разрешения, записать `idempotencyKey`, повторно прочитать, сравнить результат и отразить canonical state в связанном UI/реестре. Никакого тихого overwrite при конфликте ревизий.
- При конфликте источников сохранить оба свидетельства/редакции, выбрать приоритет по типу доказательства, показать причину и отложить опасный write. Документы `SUBMITTED/EINGEREICHT/LOCKED` и квитанции отправки immutable.
- Внутренний перевод между своими счетами имеет две компенсирующие стороны, но **0 внешнего дохода и 0 расходов**. Средства копилки физически уже находятся на счёте; внутренний резерв не прибавляет деньги. Гипотетическая зарплата в модельном плане никогда не отображается как доступная карта.
- Financial data privacy: **никаких имён, конкретных семейных сумм, номеров счетов, чеков, документов, адресов и выписок** в публичных файлах, fixtures, логах, PR/screenshots. Разрешение на работу с пользовательскими данными не является разрешением на публикацию.
- Безуспешная синхронизация должна отображать `NOT_SYNCED/ERROR`, не `COMPLETED`. Предусмотреть retry safe, backoff, dedupe, audit.
- Пользовательский ввод и подтверждения — не официальные банковские/ведомственные документы; текущие доказательства не переписывать.

## 8. Тесты и приёмка

**Базовый набор автоматических тестов**: unit, typecheck, lint, component, integration с мок-сервером коннектора и E2E для desktop/mobile. Используй обезличенный fixture, не персональные данные реального бюджета.

1. Действующие базовые доходы/расходы, шаблон, сортировка, месяц, категории, старые статусы, валюта и история не теряются после внедрения.
2. Зелёный плюс: последовательно добавляются 5 income, 7 expenses, 7 obligations, 7 goals, 7 limits. После создания корректные данные в модели, перевод в другой месяц только по явной воле, корректная сумма без дублей, reload не теряет настройки.
3. Баланс: отсутствие данных ≠ 0; два счета и внутренний перевод суммы не меняет; с копилкой резервы не удвоены; ожидаемый доход не добавлен в фактический банковский остаток.
4. Carryover: «Остаток с прошлого месяца» является ресурсом для плана и не создаёт income transaction и не увеличивает historical income; проверка перехода года.
5. Процент: plan=30, confirmed=24 → 80%; plan=30, confirmed=45 → 150% плюс overflow; plan=0 no division by zero; drafts не учитываются; точная валюта EUR.
6. Попапы меню и отдельной кнопки: keyboard, Escape, focus trap/return, touch, screen reader, backdrop. Кнопка Wallet видна отдельно от ⋯.
7. Capital без реальных накоплений — empty state, с подтверждёнными целями — корректная donut + legend + %, длинные подписи не исчезают.
8. Респонсивность при viewport 320/360/390/768/1280/1440: нет overflow, скрытых процентов, наслоения popup/карт, нечитаемых label; доступные контрасты, нет розовых блоков.
9. Connector: exact row read, write, read-after-write, ID stability, revision conflict, idempotent retry, unauthorized, offline, concurrent edit, rollback. Failures не маскировать.
10. Факт купленного или погашенного подтверждать только по доказательству. Крупный спорный платёж не будет «оплачен» только от заполнения плановой строки.

**Definition of Done**: код в исходной ветке / PR; пройденный Stage Gate; миграции (если нужны) + rollback; тесты зелёные; скриншоты обезличенных desktop/mobile; short before/after diff; отчёт о сохранности старого функционала; подтверждённое read-after-write; ссылка на commit/PR; явные статусы `DONE/PARTIAL/BLOCKED`; при незавершённой задаче не переходить дальше по roadmap.

## 9. Условие ответственности Codex

Не выполнять UI изменения, пока первичный бюджетный коннектор не завершён и не проверен. После готовности коннектора именно этот документ — приоритетный следующий этап, прежде чем продолжать остальные задачи из прежнего согласованного roadmap. Не менять произвольно текущие исходные финансовые записи пользователей. Всё, чего API не позволяет достоверно сделать, обозначить BLOCKED, не подменять текстовой имитацией.
